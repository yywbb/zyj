### ★ 最大的坑：adb 守护进程不跨工具调用存活
- 现象：`adb reverse tcp:14600 tcp:14600` 明明成功，`reverse --list` 同一次调用里能看到，
  但**下一次调用就空了**；游戏日志反复 `connection refused`
- 原因：每次 Bash/PowerShell 调用都是独立沙箱，调用结束即回收，`adb server` 随之被杀，
  reverse 映射同时失效（PowerShell 里也一样，不是 Bash 独有）
- 解法：**放到后台任务里持续维持**（后台任务可以长存活），循环里每 3 秒补一次 reverse：
  ```bash
  while true; do
    adb reverse --list | grep -q 14600 || adb reverse tcp:14600 tcp:14600
    sleep 3
  done
  ```
- 日常自己用更方便：在**普通终端**里手动跑一次 `adb reverse tcp:14600 tcp:14600`，
  守护进程在真实会话里常驻，不需要这个循环；`mock_server.py` 的 `setup_adb_reverse()` 装了 adb 后也会自动做

## 2026-10-28 凌晨：引导"卡死"根因定位（全屏遮罩）

### 现象
游戏停在「2级啦」升级弹窗 + 「前往」，画面中央一直转 `loading...`，点「前往」/「X」/任意位置全部无反应，
服务端只收到 999904 心跳，没有任何新请求。

### 根因链（三层）
1. **客户端载入遮罩永不销毁**
   `Loading_Ultimate.startGameloading(index)` 会给每个 UI 请求创建一个**全屏透明触摸拦截层**
   （touchPriority=loading，日志标签 `gameLoginprof`），只有 `stopGameloading(index)` 才摘。
   `gameloadingIdx` 只要有一项不归零，遮罩就永久残留 → 后续所有点击全被吞。
2. **服务端应答 opcode 不匹配**
   `recorded_frames.json` 里「C->S 2000」后面紧跟的是一条 **999（globalparam）主动推送**，
   被 build_routing_tables 误当成 2000 的应答。客户端永远等不到 `opcode=2000` 的应答 → 遮罩不摘。
   `2000` 有 3 组录制应答，按轮询取第 3 组时才踩坑（前两组恰好是 2000）。
3. **跨 opcode 误配对是普遍现象**
   同问题存在于 200/201/1000/1001/1032/1057/999904 等（录制把服务端主动推送归到了上一个请求的应答里）。

### 修复（mock_server.py）
普通 opcode 回放分支新增兜底：若该组应答里**没有任何 opcode == 请求 opcode** 的帧，
补发 `pack_frame(opcode, seq, b"")` 自应答，日志打印「补发自应答 ... (录制缺失, 防遮罩残留)」。
Comb(999900) 分支未动（已验证可正常初始化主城）。

### 另外两个客户端机制（重要，排查时容易误判）
- `guide.lua` ccTouchBegan：**点错满 10 次会调 `CompleteSection()` 直接跳过整段引导**，
  并上报该段最后一步。之前出现的「201 step=83 / status=2」就是被这个触发的，不是配置错位。
- "关闭弹窗"类步骤（step 10/24 等）配置是 `clickxy1="5000,5000"`（屏幕外）+ `special="hide"`，
  靠 `SpecialProcess()` 隐藏引导层让玩家自由点。`isrecover=true` 恢复路径**不会**走 SpecialProcess，
  所以这类步骤在恢复/快进到达时不隐藏 → 点击被吞。

### 本次实测引导真实轨迹（全新号）
201 上报序列：1,2,3 → 起名 → 选将 → 5,6,7 → 9,10 → 11,12,14,15,16,17,18,20,21,23 → 停在 **step 24**

## 2026-10-28 02:20 引导卡 step 24 的完整根因链（已修复）

### 一、协议帧格式（更正）
`magic(4)+body_len(4)+opcode(4)+seq(4)`，**大端** `>IIII`，共 16 字节头。
之前分析脚本写成 `magic+opcode+seq+len` 小端，导致 C->S 全部解析失败。

### 二、recorded_frames.json 是干净的，问题在服务端分组
- 410 帧 = C->S 167 + S->C 243，每条带 `c2s/opcode/seq/hex`
- 按 seq 配对校验：**167 条请求全部满足"首条应答 opcode == 请求 opcode"，零一问多答**
- 心跳 999904 的应答只有 `[(999904,0)]`，无任何附加推送
- 2000 的 5 次应答都是 1113B 真实数据
=> `build_routing_tables` 用"请求后连续的非请求帧"分组，把 seq=0 的服务端主动推送
   （999/3501/5207/1027/205/1024/111）误并进应答组，客户端收到不该收的数据 → 流程被打断。
   修复：分组后 `resps = [r for r in resps if r["opcode"] == op]`，并跳过空组。
   另加 `resp_by_seq`（seq+opcode 双重校验）优先精确回放，命中时日志打 `[seq精确]`。

### 三、轮询索引负数取模 bug（等级错乱的真正原因）
原 `candidates[(cnt-1) % len(candidates)]`，cnt=0 时 Python 得 `-1 % 6 = 5`，
第一次 1001 就返回录制末尾的 Lv.6（96B），不是 Lv.2（94B）。
修复：`candidates[cnt % len(candidates)]`。

### 四、引导卡死的客户端机制（关键，别再误判）
1. `guide.excuteGuide` 每次都 `setGuideLayerVisible(true)` + `addGuideLayer()`，
   `SpecialProcess(special=="hide")` 在**末尾**把 rootNode 设为 invisible。
   但 `setVisible(false)` **不解除触摸拦截**（registerScriptTouchHandler 不看 visible）。
2. `guide.addGuideLayer` 的 ccTouchBegan：**不在 guideRect 内**时执行
   `pTouch:setTouchInfo(touchId, -10000, -10000)` 把坐标改到屏幕外；
   `swallowsTouches=false` 所以继续下传 —— 下层的窗口按钮收到的就是 (-10000,-10000)，永远点不中。
3. touchPriority: `guide = -800`，`popwindow = -200`（且 normalPriority 每次开窗 -1，下限 -500）。
   cocos 数值越小优先级越高 => **引导层永远先于任何普通窗口收到触摸**。
4. "关闭弹窗"类步骤 step 10/24/41/50/53 配置 `clickxy1="5000,5000"`（热区在屏幕外）
   → 任何点击都不在热区 → 全部被改写坐标 → 死锁。
   step 10 之所以能过，是因为客户端在 step 9 后自发走 `7091→1001→2000`，窗口被自动关闭；
   step 23 后客户端不再发这三个请求，于是卡死。
5. `guideused` 只在点击命中热区时置 true，`errorClick` 也只在那时累加，
   所以"点错 10 次跳过引导"实际几乎不会触发（此前判断有误）。

### 五、屏幕适配参数（算坐标必备）
`scaleNum = 1152/1080 = 1.0667`；`topposY = 2376*1080/1152 = 2227.5 > 2160`
→ `fixH = (2227.5-2160)*0.5*1.0667 = 36`，`topposY` 归 2160。
`midX = Px*scaleNum`；`midY = Py*scaleNum + fixH`；下发给按钮的 y = `SCREEN_HEIGHT - midY`；
`Py` 是 `1920-y_config` 再 `-(1920-topposY)*locRate`（locRate=0.5 → +120）。
=> `clickxy1="544,1329"` 时重定向落点为设备 (580,1710)，正好是"恭喜获得"确定按钮中心。
