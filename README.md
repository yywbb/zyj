# 《作妖计》(ZuoYaoJi) 本地单机模拟服与逆向工程套件

本仓库提供《作妖计》(Cocos2d-x + Lua + Protobuf 架构) 手游的完整本地单机化运行环境、离线模拟服务端、逆向分析资源以及自动化重打包脚本。

---

## 🌟 核心特性

- **局域网直连，无需 ADB**: 安卓手机与电脑模拟器使用同一份 APK，直接连接电脑的固定局域网 IP 和统一端口 `14600`；不依赖 USB 调试或 `adb reverse`。
- **多账号独立存档**: 复用登录页选服界面选择“账号 1、账号 2 …”，每台设备记住自己的选择。一个服务端同时处理不同账号；同一个账号只允许一个在线连接，避免覆盖进度。这是独立存档多开，不提供账号间交易、组队等共享世界功能。
- **本机 GM 工作台**: 总览、玩家筛选与分栏档案；离线调整资源、发放道具/碎片/普通装备/招募池武将；操作流水、备份恢复及配置原始值对比。
- **全流程新手引导支持**: 完整保留原汁原味的游戏体验，包括开场剧情漫画（1~8幕）、起名与随机名字生成、3选1初始武将、新手第一战（黄泉路对阵小野鬼回合制战斗）、升级结算与主线地府大地图。
- **自研战斗 v2**: 招募武将可自由上阵，按同一引擎实时挑战全部普通主线（62章、310图、3061关），包含治疗、增减益、突破、魔罩、真实胜负、掉落与升级，以及三星后的单次/批量扫荡；采用的自研规则见 [battle_rules.md](battle_rules.md)。
- **本地模拟充值与封神招募**: 点击充值档位直接确认本地支付成功，按配置发元宝、VIP及首充/月卡权益；封神支持单抽、十连预览、重抽和确认领取，未领取结果重登保留。
- **渐进式角色持久化存档 (`role_save.json`)**:
  - 实时捕获并记录玩家自定义起名（Opcode 101）；
  - 实时记录玩家所选初始武将（Opcode 202）；
  - 实时记录新手引导与剧情步数（Opcode 201 `guide.step`）；
  - 支持中途退出后的**断点无缝续存**；
  - 账号 1 沿用 `role_save.json`，其他账号使用 `accounts/<编号>/role_save.json`；可按账号重置，引导与角色快照互不影响。
- **Comb Signature 复合路由**: 客户端 `Opcode 999900` (`CombMessages`) 按子消息 ID 集合与完整请求载荷匹配，兼容 Comb 封装、引导 `201` 及上阵 `1003` 的 Protobuf 字段顺序差异，区分主城 26/30 模块、功能列表和不同关卡；录制段之间隔离应答序号，避免混合采集后重复回包。
- **TCP 流重组还原 (TCP Stream Reassembly)**: 彻底修复抓包中超过单帧 MTU 限制的分包数据（4,101 字节全量主城包），根除 Protobuf 反序列化时触发的 `decoder:247 Truncated message` 致命错误。
- **全量离线配置内置**: 将从官方 CDN 提取的 1,244+ 个 JSON 数据表注入 APK assets 中，彻底解决离线时缺少 `guide_step.json` / `guide_section.json` 导致的黑屏崩溃。
- **自动化秒级打包流水线**: `build_local_apk.py` 使用 Python 原生 zip 操作与 `apksigner`，绕过容易出现资源解析崩溃的 Apktool 回编译，数秒内完成改包与 V1/V2 签名。

## 🛠️ 网络协议与封包规范

### 1. 基础包头结构 (16 字节)
通信基于 TCP 二进制协议，每个数据包均包含 16 字节固定大端包头：

| 偏移 | 字段名 | 类型 | 字节序 | 描述 |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | Magic | `uint32` | Big-Endian | 协议魔数，固定为 `0x0000EE1C` |
| `0x04` | Length | `uint32` | Big-Endian | 后续载荷 (Payload) 字节长度 |
| `0x08` | Opcode | `uint32` | Big-Endian | 协议操作码 (例如 `1000` 登录, `200` 引导) |
| `0x0C` | Seq | `uint32` | Big-Endian | 请求序号 (客户端发起递增，服务端原样应答) |

### 2. 核心协议交互流程
```mermaid
sequenceDiagram
    autonumber

    C->>S: Opcode 1000 (选择账号并绑定连接)
    S-->>C: Opcode 1000 (队列状态: 0 无需排队)
    
    C->>S: Opcode 200 (引导查询, param="first")
    Note over S: 读取本次登录账号的独立存档
    alt 全新账号 (未建号)
```

## 🚀 快速上手

### 1. 环境准备
- 操作系统: Linux / macOS / Windows (WSL)
- Python 3.8+
- 安卓手机或安卓模拟器，能访问服务端电脑所在的可信局域网或虚拟组网；无需开启 USB 调试
- 仅重打包时需要：原版 `z7_7_4.apk`、Java Runtime 和 Android SDK build-tools (`zipalign`、`apksigner`)
- 建议在路由器为服务端电脑保留固定 IP；电脑防火墙只对可信局域网放行 TCP `14600`，不要设置公网端口转发

### 2. 构建一次局域网客户端

默认使用 `10.66.0.x` 虚拟组网，电脑和手机均需保持组网连接：

- 游戏服务端：电脑 **`10.66.0.12:14600`**。
- 无线调试：手机 **`10.66.0.50:5555`**（`NOH-AN00`）。

2026-10-29 已从手机连续三次直连该游戏端口并收到预期协议回包（61–87 ms），同时验证无线 ADB 可执行命令；期间一次组网短暂掉线，恢复后复测通过。地址重新分配后需重新确认。

把原版 `z7_7_4.apk` 放在脚本旁，指定**服务端电脑**的 IP：

```bash
python3 build_local_apk.py --server-ip 10.66.0.12 --accounts 3
```

`--server-ip` 必填，只接受局域网 IPv4，拒绝回环地址和公网地址；`--accounts` 默认为 2，范围 1~1000，只控制登录页的预设账号列表。登录表单可输入任意 1~1000 的已启用账号，后台新增账号无需重打包。所有账号共用同一个 IP 和端口；电脑 IP 改变后需要重新打包、更新客户端。

### 3. 启动统一服务端
```bash
# 监听 0.0.0.0:14600，不调用 ADB
python3 mock_server.py
```
保持服务端运行，再进入游戏。能播放本地开场剧情并不表示已连上游戏服务；服务未启动时，随机取名和建号请求无法正常完成。

在运行服务端的电脑上打开 **http://127.0.0.1:14601** 进入管理后台。后台与游戏共用一个进程和账号占用表，随服务端退出而关闭。端口冲突时可用 `--admin-port 14602`；指定 `0` 会自动分配端口，以启动日志中的地址为准。

#### 空回复与错误诊断

服务启动后自动写入仓库内 **`logs/diagnostics.log`**，每行一条 JSON，实时追加；每份约5 MiB，保留当前文件及 `.1`～`.3` 三份旧日志。启用此功能只需重启服务端。

- `error_response`：原生 `999999` 拒绝，附错误码和 `1999` 中文原因；`exception`：登录、请求处理、保存或发送异常，附阶段及调用栈。
- `empty_response`：零字节回包和 Comb 内的空子包，仅记为 **INFO**，不代表失败；正常空心跳 `999904` 略过。`no_response` 表示处理结果没有任何回复，`invalid_response` 表示诊断发现回包格式异常。
- 记录 UTC 时间、账号、客户端地址、请求 opcode/seq、请求 hex/可直接识别的 Ids 参数及响应长度。单个请求体最多记录4096字节，超长标记 `truncated`；Comb 列出子请求，保留顺序。登录、未认证请求和支付凭证不记录内容；含登录/嵌套 Comb 或无法解析的 Comb 整体脱敏。
- `phase=response` 是已发送的响应组；`phase=handle/send/login/receive` 的异常记录用于定位发生阶段，其中 `responses` 可能只是已准备的回包。日志失败只提示，不阻断游戏或改变保存结果；存档失败仍按原逻辑断开连接。

复现问题后，提供发生时间、账号、页面/按钮，以及当前日志和同期轮转文件即可。实时查看：

```bash
tail -f logs/diagnostics.log
```

五项充值活动的历史排查和客户端字段依据见 [活动补录清单](activity_capture_20261029.md)；当前实现范围以本文“日常活动充值页签”为准。

### 4. 创建账号并登录

先在管理后台打开一个 1~1000 的账号编号，输入并确认密码，点击“创建登录账号”；原有存档点击“绑定密码，保留进度”。密码为 8~64 位英文字母、数字或符号，不含空格。账号编号就是登录名，没有默认密码、游客绕过或客户端自由注册。

把同一份新版 `zyj_local.apk` 传到手机、导入模拟器安装，点击图标启动。首次在原生表单输入账号编号和密码；服务端认证成功后记住这一组凭据，下次启动等待2秒自动进入，可点击“切换账号”取消并打开表单。认证拒绝会清除记住的密码；连接失败保留凭据，停止本轮自动尝试，确认提示后回表单重试。手机、模拟器使用不同账号可同时游玩；换设备时输入原账号密码续玩，需先退出原设备。自用局域网版通过 `CCUserDefault` 明文保存凭据，密码框保持掩码且不打印输入内容。

服务端验证密码后才占用账号并读取存档。旧版仅发送账号编号的客户端会被拒绝，必须重新构建并安装 APK。同一账号一分钟内连续失败五次后暂停登录一分钟，其他账号不受影响。当前版本不提供密码修改或找回，请妥善保管密码。

ADB 可以仅用于可选的安装和日志调试，游戏连接不经过它：

```bash
adb connect 10.66.0.50:5555
adb -s 10.66.0.50:5555 install -r zyj_local.apk
adb -s 10.66.0.50:5555 shell monkey -p com.ldfs.zyjyg.local -c android.intent.category.LAUNCHER 1
```

若无法连接，检查 IP 是否正确、防火墙是否允许该端口、Wi-Fi 是否启用了访客隔离或客户端隔离。异常断网后旧会话需等待 TCP 断开才能释放；首版不自动踢旧会话接管。

### 5. 按账号重置

也可从命令行重置：先停止正在运行的服务端，再执行以下命令。操作前自动备份目标存档，重置后仍会启动统一服务端：

```bash
python3 mock_server.py --account 2 --reset
python3 mock_server.py --account 2 --reset-guide
```

两条命令分别表示清空账号 2 的全部进度、仅清空账号 2 的引导。未指定 `--account` 时仍以账号 1 为目标，不影响其他账号。所有存档相对脚本目录；在新 worktree 或复制工程中启动时，不会自动读取旧目录的存档，迁移前请停服并备份。

### 6. GM 工作台、账号维护与配置编辑

**工作台总览**展示账号、在线玩家、已建角色、档案异常数及配置版本和最近操作。**玩家管理**列出已设置密码、已存档、在线或有备份的账号，支持账号/角色名搜索、在线状态与最低等级筛选、每页 25 条；输入 1～1000 的编号即可打开或创建。玩家档案通过页签展示角色资源、武将阵容、装备背包、副本与引导、模拟充值/月卡、活动领取和招募冷却。副本宝箱区分未达标、可领取与已领取。点击“刷新数据”更新；查询不会触发体力恢复或修改存档，在线数值以游戏最后一次成功保存为准。

**GM 调整与发放**先读取离线玩家，再填写资源增减量、选择物品并填写原因。支持元宝、银币、体力、精力的非零整数增减，最终余额必须在 0～2147483647 内；GM 元宝修正不增加消费活动进度或充值/VIP权益。体力在提交时按同一时间结算离线恢复，允许合法超上限。物品目录按运行中的配置搜索名称/ID，支持道具、有效武将碎片、普通四类装备，以及现有招募池的基础武将；重复武将按现有招募规则转碎片，发武将需先完成新手引导。最多 32 种物品，每种道具/碎片最多 1000000，装备与武将合计最多 100 个。入库不代表道具使用功能已实现。

**背包管理**在玩家档案的“背包”页签中按名称、配置 ID 或道具/碎片类型筛选，点击“调整数量”填写目标总量（0～2147483647），可用增减按钮或“清空”。修正数量只改库存，不触发道具使用、碎片合成或奖励效果。碎片页显示可发放的碎片道具 ID，内部转换为存档中的武将 ID。GM 发放页提供体力丹、精力丹、三类招募令和四类经验丹的快捷入口，点击后加入发放清单，再填写数量与原因。

**英雄管理**在“武将与装备”页签筛选已上阵、闲置、助阵武将，展开名称可查看配置/实例 ID、品质、经验、潜力和战斗属性。完成新手引导后可离线执行：

- **升级**：填写高于当前等级且不超过角色等级限制的目标等级，不消耗经验丹；复用游戏成长计算，同步属性、潜力、主角快照和阵容战力，保留培养加成。助阵或尚未支持的高级属性武将拒绝修改。
- **上阵 / 下阵**：选择已解锁阵位或下阵；替换闲置武将继承阵位装备，移动已上阵武将交换整套阵位与装备，按当前成员重算缘分差值；主角必须留在阵中。
- **移除**：仅移除非主角的闲置武将及其培养进度，不返还材料或碎片；上阵、助阵武将须先处理阵位。需要撤销时恢复该次操作前的备份。

上述操作统一经 `Workbench.apply(account, data)`，使用相同的离线锁、版本检查、备份、操作回执与流水。原发放请求保持兼容；管理请求带 `action`：`inventory`（`cid`、目标 `count`）、`general-level`（`iid`、目标 `level`）、`formation`（`iid`、目标 `position`，0 表示下阵）或 `remove-general`（`iid`），以及通用的 `operation_id`、`revision`、`reason`。同一请求只执行一个管理动作。页面在请求结果未确认时保留原编号，并提供查询/重试入口。

每次 GM 操作校验离线状态与存档版本，在副本上准备全部变更，先备份，再通过游戏的统一保存入口同步资源、背包、角色快照和体力时钟；重登后生效。请求使用唯一操作编号，同编号同参数重试只返回原结果。页面在会话存储中保留未确认请求，刷新后可按原编号查询/重试。`gm_operations/<操作ID>.json` 保存意图和结果，`gm_receipt` 随存档原子写入，发放已保存但最终日志写失败时可据此确认成功；无法确认的中断操作显示“待核对”，不会自动重新执行。

**操作记录**可按账号、类型和日期筛选，查看 GM 实际变更、前后版本、结果与备份编号；同时记录网页创建账号、备份、恢复、重置和配置修改。流水独立于游戏存档，恢复旧存档不会删除记录或让已成功的请求重复发放；不记录密码、盐或哈希。迁移工程时一并保留 `gm_operations/`，该目录不提交 Git。当前操作者统一为本机管理员，记录从启用此版本后开始。

登录凭据独立保存在 `accounts/<编号>/credentials.json`，使用随机盐和 600000 次 PBKDF2-SHA256，原子落盘；后台响应不包含密码、盐或哈希。设置密码立即生效，不创建或改写游戏存档。已有凭据禁止覆盖，在线账号禁止绑定。进度重置、恢复、下载均不包含或改动凭据；迁移工程时需同时保留凭据文件和存档（均不提交 Git）。

退出目标账号的游戏连接后，可创建备份、重置引导、重置账号或选择备份恢复；其他账号可继续游玩。登录与维护共用锁，在线账号拒绝维护。操作核对存档版本，页面过期时刷新重试。重置和恢复会先把当前文件备份到 `backups/accounts/<编号>/<备份ID>.json`；备份失败则停止操作。恢复前通过游戏存档校验，保存失败保留原文件。重置后仍可从账号列表找到备份并恢复。“下载存档”只导出当前文件，也可用于保留损坏文件。

重置引导只清除引导历史，保留角色、背包与奖励领取记录，不会重新发奖；完整新号体验使用“重置账号”。

**游戏配置**支持分类、配置表、ID或文本浏览，展开条目可比较原始值与本地覆盖，编辑弹窗显示中文字段和原始值；当前只允许编辑：

| --- | --- | --- |
| `props` | 20014 / 20019 / 20015 / 20020 | 恢复量、道具说明 |
| `begin7day_task` | 80001 / 80030 | 首日奖励、名称 |

奖励格式为 `物品ID,数量;`，只接受已实现的银币、元宝、道具、碎片和装备；未知物品、重复条目及越界数量会被拒绝。保存只写 `config_overrides.json`，原 ZIP 保留，旧覆盖备份到 `backups/configs/`；“恢复原配置”移除该条目的覆盖。

## 🔍 逆向关键避坑指南 (Troubleshooting)

1. **Protobuf 报错 `[Lua "decoder:247"] Truncated message`**
   - **原因**: 复合协议 `Opcode 999900` 长度达到 4,101 字节，抓包时跨越了 3 个 TCP 分段（MTU 1500 限制）。若未做 TCP 流重组直接保存，会导致数据包被腰斩。
   - **解决**: 使用 TCP 流重组算法（`mock_server.py` 已内置修复后的全量数据），保证 26 个子模块的反序列化完整性。

2. **启动卡在“加载配置文件”或闪退**
   - **原因**: 原版游戏依靠 CDN 动态热更拉取 `guide_step.json`、`guide_section.json` 等配置，单机环境访问外网 CDN 失败会导致配置为空指针崩溃。
   - **解决**: 已将官方 CDN 的全量 1,244 个 JSON 配置文件直接打包内置于 `zyj_local.apk` 的 assets 目录下。

3. **多次重连后界面功能错位**
   - **原因**: 简单回放服使用单纯计数器轮询 `resp_map`，一旦发生跳步或重连，序号错位会导致将“选将包”错回给“主城界面”。
   - **解决**: 组合请求按子模块 ID 集合与完整请求载荷匹配，区分同一协议下的不同关卡、招募和上阵参数，不再按连接序号选择组合响应。普通回放的序号命中和备用路由都核对 opcode 与完整载荷，计数按参数隔离，不能用其他参数的录制响应兜底。未实现或未匹配的请求统一返回原生错误，不执行其他录制操作的推送、奖励或扣费，也不再补空成功包。

本地登录（1000）由 TCP 入口校验 `local_account_<编号>` 与密码后绑定独立存档，不使用录制登录响应；仅用于可信局域网，TCP 传输尚未加密。同参数对应的多份录制响应仍按连接内次数轮询，尚不等于完整业务实现。

实机首战曾因 Protobuf 字段顺序不同而返回空组合包：Comb 子消息的 `id/data`、引导 `201` 的 `section/step` 与抓包顺序相反，但值相同。录制索引和实时请求现在统一规范这些消息及上阵 `1003`（`GeneralChangePos`）的字段顺序，共用参数计数；子消息顺序、同字段重复值顺序、未知字段和重复字段均保留，其他子消息的 data 仍按完整字节匹配。新增回归覆盖实机原始首战请求、首战奖励与引导重连、上阵字段换序后的阵容持久化、全教程 Comb 字段换序，以及修改参数或添加字段不改存档。

混合录制按客户端请求序号回退（含重用相同序号）分段，同段内按序号与 opcode 匹配跨请求到达的应答，不跨段拼接。精确索引保留 `(seq, opcode, 完整载荷)` 对应的各份响应组，不让后来的采集覆盖旧记录；精确键有歧义时仍使用按参数隔离的连接内计数，不合并成多份应答。当前录制格式没有连接标签，独立采集若序号没有回退，需补充标签后再导入，不能靠此规则识别所有连接边界。

初始化同样要求完整录制参数匹配，不再对任意大型 Comb 套用通用模板。已匹配的 26/30 项初始化保留各自模块顺序；公共模块先取录制中一级新号的基础，再回填本地存档，只额外补齐新采集中的空扩展 `8101/8105/8109/8110`，不播放第二天完成账号的背包、主角或功能快照。缺少新号基础或发现尚未支持的非空扩展时，拒绝构建路由。新增第二天礼包采集不代表开放 `80002` 或日/周重置业务。
